開発と運用の土台とAPIの形を、兄弟製品のMadoにそろえました。監査ログの値の名前を変え、Webのnginxを非rootで動かし、APIはビルドしたJavaScriptで動かします。APIのエラー応答は英語の文とcodeになり、ヘルスチェックは`GET /healthz`に、API tokenの前置きは`mado_mt_`（Job tokenは`mado_mtj_`）になりました。**発行済みのAPI tokenはすべて使えなくなるので、更新後に発行し直してください。**

設定の環境変数の名前は、すべて`MMT_`で始まる形になりました（`AUTH_MODE`→`MMT_AUTH_MODE`、`S3_BUCKET`→`MMT_S3_BUCKET`など）。**更新する前に、`.env`と`compose.override.yml`の名前を付け替えてください**（[環境変数の名前の付け替え](#環境変数の名前の付け替え)）。

## 変更点

### API

- 監査ログ（AuditEvent）の`outcome`の`failed`を`failure`に、接続元の項目`ip`を`ipAddress`に変えました（DBの列は`ip_address`）。`GET /audit-events`・`GET /projects/:p/audit-events`の`outcome`の絞り込みも`failure`を使います。既存の記録はDBの更新（`071_audit_failure_and_ip_address.sql`）で書き換えます。
- `docs/openapi.json`と`GET /api/openapi.json`の`info.version`が、契約の版（`0.1`）ではなくアプリの版になりました。
- 独自APIのエラー応答を`{"error": <英語の文>, "code": <理由の名前>}`にそろえました。`error`は今まで日本語でしたが、英語になります。文に入る値（足りないscope、parameter名、上限など）は`error`・`code`の横の項目にも入ります（例: `scope_required`の`scope`・`purpose`、`invalid_request`の`fields`）。codeの一覧は`@mmt/contracts`の`API_ERROR_CODES`で、OpenAPIのエラー本文のschema名は`ApiError`から`ApiErrorBody`に変わりました。MLflow互換APIは今までどおり`{"error_code", "message"}`で、`message`が英語になります。
- Madoと同じ意味のcodeは同じ名前にしました。

  | 旧 | 新 |
  | --- | --- |
  | `insufficient_scope` | `scope_required` |
  | `invalid_parameter_value`（Runの検索式・cursorなど） | `invalid_request` |
  | `resource_already_exists` | `already_exists` |
  | `invalid_range` | `range_not_satisfiable` |
  | `last_global_admin` | `last_active_admin` |
  | `local_account_required` | `local_credential_unavailable` |
  | `scope_exceeds_issuer` | `token_authority_exceeded` |
  | パスワード変更で現在のパスワードの誤り: 401 `invalid_credentials` | 400 `incorrect_password` |

- Sweepの探索空間とearly_terminateの誤り（`sweep_space_invalid`・`sweep_early_terminate_invalid`）は、`reason`（`values_empty`・`range_order`など）と`parameter`などの項目で理由を示します。
- ヘルスチェックの`GET /health`と`GET /api/health`をやめ、`GET /healthz`（`/api`の外、認証なし）が`{"status":"ok"}`を返すようにしました。DBに届かなければ503 `database_unavailable`です。
- API token（個人・Service Account・worker・launcher）の値は`mado_mt_`、Job tokenは`mado_mtj_`で始まります。認証はこの形の値だけを受け付け、`mmt_`・`mmtj_`で始まる値は401 `invalid_token`です。一覧に出す先頭は16文字（前置きと8文字）になりました。

### Web

- 画面の応答に、Content-Security-Policy、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`を付けます。外部のサイトから画面を読み込むことはできません。
- APIのエラーは、日本語の画面ではcodeから訳した文を出します。訳の無いcodeはAPIの英語の文を出し、`invalid_request`などの理由の幅が広いcodeは日本語の文のあとにAPIの英語の文を括弧で添えます。英語の画面はAPIの英語の文を出します。

### コンテナ・Compose

- Webのイメージは`nginxinc/nginx-unprivileged`になり、nginxはroot以外で動きます。コンテナの中で待ち受けるportは80から8080に変わりました。ホスト側（`127.0.0.1:5182`）は変わりません。
- APIとプレビュー用workerのイメージは、TypeScriptをビルドしたJavaScriptを`node`で動かします。イメージにはTypeScriptのソースとビルドの道具が入りません。`npm run db:migrate -w @mmt/api`などのコマンドは今までどおり使えます。
- 全イメージのベースイメージをdigestで固定しました。
- `compose.yml`にproject名（`name: mado-model-tracking`）を入れました。展開先のディレクトリ名にかかわらず、同じコンテナとvolumeを使います。
- `api`にヘルスチェック（`GET /healthz`）を付け、`web`は`api`がhealthyになってから起動します。Webのnginxとedgeのrunner用nginx（`deploy/edge/runner-api.conf.template`）は`/healthz`もAPIへ渡します。edgeでは今までの`/api/health`と同じく、Job tokenのあるrunnerにだけ答えます。

### 設定（環境変数）

- APIとプレビュー用workerが読む環境変数の名前を、すべて`MMT_`で始まる形にしました（兄弟製品のmado S3 Data Catalogは`MDC_`）。旧い名前は読みません。対応は[環境変数の名前の付け替え](#環境変数の名前の付け替え)の表のとおりです。値の形は変わりません。
- 旧い名前だけが設定され、新しい名前が無いと、API・プレビュー用worker・`db:migrate`・`bootstrap-admin`・`backfill-run-media`は`Old environment variable names are set: AUTH_MODE was replaced by MMT_AUTH_MODE`のように、残っている旧名と新しい名前を並べて起動しません。表示するのは名前だけで、値は表示しません。今までの`DATABASE_URL`（→`MMT_DATABASE_URL`）と`OIDC_ADMIN_GROUP`（→`MMT_OIDC_ROLE_MAPPING_JSON`）の検査もここにまとめました。新しい名前もあるときは新しい名前を使い、旧名は無視します。
- Webのイメージのビルド引数`VITE_GIT_COMMIT`・`VITE_GIT_DATE`（「このアプリについて」に出すコミットと日時）を、`MMT_GIT_COMMIT`・`MMT_GIT_DATE`にしました。
- `MLFLOW_TRACKING_URI`・`MLFLOW_TRACKING_TOKEN`などMLflowのクライアントの標準の変数、AWS SDKの`AWS_*`、Postgresのイメージの`POSTGRES_*`、`NODE_ENV`は変わりません。SDK・worker・launcherが読む変数（`MMT_API_URL`、`MMT_API_TOKEN`、`MMT_WORKER_*`など）は元から`MMT_`で始まっているので、変わりません。

### SDK・worker・launcher

- `mado-tracking-worker doctor`とコンピュータの接続確認は、`MMT_API_URL`の`/api`を外した`/healthz`でAPIへの到達を確かめます。
- workerとrunnerは`mado_mtj_`で始まるJob tokenだけを受け付けます。v0.4.0までのworker・launcherは新しいAPIが発行するJob tokenを受け付けないので、APIと一緒に更新してください。

### そのほか

- Apache License 2.0のLICENSEとNOTICEを付けました。配布物にも入ります。

## 互換性と更新手順

更新前にDBをバックアップしてください。

1. Webのportを書き換えている場合（`compose.override.yml`の`ports`など）は、コンテナ側の番号を80から8080へ直します。例: `'0.0.0.0:80:80'`→`'0.0.0.0:80:8080'`。
2. v0.4.0までの配布物（bundle）から入れた環境は、Composeのproject名が展開先のディレクトリ名（例: `mado-ml-tracking-v040`）になっています。`docker compose ls`で今の名前を確かめ、`.env`に`COMPOSE_PROJECT_NAME=<その名前>`を書いてから更新します。書かないと新しい空のvolumeで起動します。リポジトリを`mado-model-tracking`というディレクトリに置いて動かしている環境は、そのままで同じ名前です。
3. `.env`と`compose.override.yml`の環境変数の名前を付け替えます（[環境変数の名前の付け替え](#環境変数の名前の付け替え)）。Composeを使わずに動かしている場合は、APIとプレビュー用workerに渡している環境変数を同じ表のとおりに直します。
4. 動いているJobを終わらせるか止めます。DBの更新（072）でJob tokenも失効するので、動いたままのJobはAPIへ記録できなくなります。
5. APIとプレビュー用workerを止め、新しいイメージでDBを更新してから（`071_audit_failure_and_ip_address.sql`、`072_token_prefix.sql`）、新しいAPI・プレビュー用worker・Webを起動します。071は監査ログの列名を変えるので、v0.4.0のAPIとは両立しません。Webのコンテナも入れ替えてください。
6. 072は、発行済みのAPI tokenとJob tokenをすべて失効させます（監査ログの`token.revoke`に、`details.reason`が`token_prefix_changed`の記録が残ります）。使っていたものは発行し直して差し替えます。
   - 個人のtoken・Service Accountのtoken: ［プロジェクト設定］の［API tokenを発行］かService Accountの画面で、同じ用途・scopeで発行します。SDK・MLflowの`MMT_API_TOKEN`・`MLFLOW_TRACKING_TOKEN`、学習のジョブが読むenv file、CIの設定などを新しい値に替えます。tokenを秘密の管理の仕組みに置いている場合は、そこに入れ直します。
   - worker: Service Accountでworker用のtokenを発行し、`mado-tracking-worker install --token-file`（Composeの`worker`は`MMT_WORKER_TOKEN_FILE`、既定は`var/worker-token`）で差し替えます。
   - launcher: 全体管理の「ランチャー」で各launcherの［tokenを作り直す］を押し、`launcher.toml`の`token_file`が指すファイルを新しい値に差し替えます。
7. ヘルスチェックを`/health`か`/api/health`で見ている監視は、`/healthz`に直します。Webの`127.0.0.1:5182/healthz`でも確かめられます。
8. APIのエラーの`error`の文や、上の表の旧いcodeを見ているスクリプトは、新しいcodeで判定するように直します。
9. 監査ログをAPIで読んで`outcome`の`failed`や`ip`を見ているスクリプトは、`failure`と`ipAddress`に直します。
10. Composeを使わずにソースから動かしている場合は、`npm run build -w @mmt/api`でAPIをビルドしてから、`npm run db:migrate -w @mmt/api`・`npm run start -w @mmt/api`を実行します。

worker・launcher・SDKは、Job tokenの前置きとヘルスチェックの経路が変わったので、APIと同じv0.5.0にそろえてください。

すでに`MMT_`で始まっている変数（`MMT_DATABASE_URL`、`MMT_PUBLIC_URL`、`MMT_WEB_ORIGIN`、`MMT_STORAGE_SECRET_KEY`、`MMT_POSTGRES_PASSWORD`、`MMT_TOKEN_DEFAULT_LIFETIME_DAYS`、`MMT_FILESYSTEM_STORAGE_DIR`など）と、`COMPOSE_FILE`・`COMPOSE_PROJECT_NAME`・`NODE_ENV`は変わりません。保存先の認証情報を暗号化する鍵`MMT_STORAGE_SECRET_KEY`は、名前も値も今のままにします（値を変えると、保存済みの暗号文が読めなくなります）。

**`compose.override.yml`の`AUTH_MODE`は必ず直してください。** `compose.yml`の`api`は`environment`で`MMT_AUTH_MODE: oidc`を渡し、これは`.env`より優先されます。`local`か`hybrid`で動かしている環境は、`compose.override.yml`の`api`の`environment`に`AUTH_MODE: local`などを書いているはずです。これが旧い名前のままだと無視され、APIは`oidc`で起動しようとして`MMT_OIDC_ISSUER_URL and MMT_OIDC_CLIENT_ID are required when MMT_AUTH_MODE=oidc`で止まります。同じように`HOST`・`PORT`・`ARTIFACT_FILESYSTEM_ROOT`は、`compose.yml`とイメージが新しい名前で値を渡すので、旧い名前が残っていても起動時の検査では見つかりません。下の手順で全部付け替えます。

### 手順

`.env`のあるComposeのディレクトリで、APIを止める前に行います。ファイルを書き換えるだけなので、動いているコンテナは作り直すまで今の設定で動き続けます。値には認証情報が入っているので、画面に出しません。`cat .env`や、絞り込まない`docker compose config`は値を表示するので使いません。

1. 2つのファイルをバックアップします。

   ```sh
   umask 077
   backup="var/backups/env-names-$(date +%Y%m%d-%H%M%S)"
   mkdir -p "$backup"
   cp -p .env "$backup/"
   if [ -f compose.override.yml ]; then cp -p compose.override.yml "$backup/"; fi
   ```

2. 今の名前を確かめます。名前だけを表示し、値は表示しません。

   ```sh
   grep -oE '^[A-Za-z_][A-Za-z0-9_]*=' .env | tr -d '=' | sort
   if [ -f compose.override.yml ]; then
     grep -noE '^[[:space:]]+(- )?[A-Za-z_][A-Za-z0-9_]*[:=]' compose.override.yml
   fi
   ```

3. 表のとおりに名前を付け替えます。`.env`は`旧名=`で始まる行、`compose.override.yml`は`旧名:`（mapの形）か`- 旧名=`（listの形）の行だけを書き換えます。

   ```sh
   renames='
     HOST:MMT_HOST
     PORT:MMT_PORT
     AUTH_MODE:MMT_AUTH_MODE
     AUTH_SESSION_IDLE_SECONDS:MMT_AUTH_SESSION_IDLE_SECONDS
     AUTH_SESSION_ABSOLUTE_SECONDS:MMT_AUTH_SESSION_ABSOLUTE_SECONDS
     OIDC_ISSUER_URL:MMT_OIDC_ISSUER_URL
     OIDC_CLIENT_ID:MMT_OIDC_CLIENT_ID
     OIDC_CLIENT_SECRET:MMT_OIDC_CLIENT_SECRET
     OIDC_SCOPES:MMT_OIDC_SCOPES
     OIDC_ALLOWED_GROUPS:MMT_OIDC_ALLOWED_GROUPS
     OIDC_ROLE_MAPPING_JSON:MMT_OIDC_ROLE_MAPPING_JSON
     OIDC_DEFAULT_ROLE:MMT_OIDC_DEFAULT_ROLE
     OIDC_AUTO_LINK_VERIFIED_EMAIL:MMT_OIDC_AUTO_LINK_VERIFIED_EMAIL
     OIDC_LABEL:MMT_OIDC_LABEL
     OIDC_ALLOW_INSECURE_HTTP:MMT_OIDC_ALLOW_INSECURE_HTTP
     OIDC_RECHECK_SECONDS:MMT_OIDC_RECHECK_SECONDS
     OIDC_TOKEN_SYNC_MAX_AGE_SECONDS:MMT_OIDC_TOKEN_SYNC_MAX_AGE_SECONDS
     DEVELOPMENT_ADMIN_EMAIL:MMT_DEVELOPMENT_ADMIN_EMAIL
     ARTIFACT_FILESYSTEM_ROOT:MMT_ARTIFACT_FILESYSTEM_ROOT
     S3_BUCKET:MMT_S3_BUCKET
     S3_ENDPOINT:MMT_S3_ENDPOINT
     S3_REGION:MMT_S3_REGION
     S3_PREFIX:MMT_S3_PREFIX
     S3_FORCE_PATH_STYLE:MMT_S3_FORCE_PATH_STYLE
     S3_ACCESS_KEY_ID:MMT_S3_ACCESS_KEY_ID
     S3_SECRET_ACCESS_KEY:MMT_S3_SECRET_ACCESS_KEY
   '
   for pair in $renames; do
     old=${pair%%:*}
     new=${pair#*:}
     sed -i -E "s/^${old}=/${new}=/" .env
     if [ -f compose.override.yml ]; then
       sed -i -E "s/^([[:space:]]+(- )?)${old}([:=])/\1${new}\3/" compose.override.yml
     fi
   done
   ```

4. 旧い名前が残っていないかを確かめます。何も表示されなければ付け替え終わりです。

   ```sh
   old_names=$(for pair in $renames; do printf '%s|' "${pair%%:*}"; done)
   old_names=${old_names%|}
   grep -noE "^(${old_names})=" .env
   if [ -f compose.override.yml ]; then
     grep -noE "^[[:space:]]+(- )?(${old_names})[:=]" compose.override.yml
   fi
   ```

5. Composeが`api`に渡す名前を確かめます。名前の一覧と、認証方式（`MMT_AUTH_MODE`）だけを表示します。名前がすべて`MMT_`で始まり（`NODE_ENV`を除く）、`MMT_AUTH_MODE`が今使っている方式（`local`など）になっていればよいです。

   ```sh
   docker compose config --format json | python3 -c '
   import json, sys
   environment = json.load(sys.stdin)["services"]["api"]["environment"]
   print("\n".join(sorted(environment)))
   print("MMT_AUTH_MODE =", environment.get("MMT_AUTH_MODE"))'
   ```

v0.4.0のイメージは旧い名前しか読みません。v0.4.0へ戻すときは、バックアップから2つのファイルを戻します（`cp -p "$backup/.env" .env`、`compose.override.yml`も同じ）。

worker・launcher・SDKの設定は変わりません。

- systemdで動かすworkerの環境変数のファイル（`/etc/mado-tracking-worker/<worker-id>.env`、user unitは`~/.config/mado-tracking-worker/`）と、launcherの`launcher.toml`は、そのまま使えます。
- Composeの`worker`・`launcher`のprofileの`MMT_WORKER_*`・`MMT_LAUNCHER_*`も、そのままです。
- SDK・学習のジョブの`MMT_API_URL`・`MMT_API_TOKEN`と、MLflowのクライアントの`MLFLOW_TRACKING_URI`・`MLFLOW_TRACKING_TOKEN`も、名前はそのままです（tokenの値は、更新手順の6で発行し直したものに替えます）。
